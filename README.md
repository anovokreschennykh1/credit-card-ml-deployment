# ML Implementation - AB in "Credit Card Default Prediction Service"
Разработка и внедрение сервиса прогнозирования дефолта по кредитным картам с контейнеризацией и A/B-тестированием

## Цель проекта
Разработать и внедрить в production-like-среду сервис машинного обучения для прогнозирования дефолта по кредитным картам, который охватывает полный цикл от сохранения модели до организации A/B-тестирования.

## Структура проекта
```text
.
├── app/
│   ├── __init__.py
│   └── api.py                  # Flask API: эндпоинты /predict и /health
├── models/
│   ├── _model_v1.pkl            # модель для контрольной группы A: GradientBoostingClassifier
│   └── _model_v2.pkl            # модель для тестовой группы B: LogisticRegression
├── notebooks/
│   └── Model_selection.ipynb    # обучение, сравнение моделей и сохранение в pickle
├── screenshots/                # скриншоты тестовых запросов и ответов API
├── Dockerfile                  # сборка Docker-образа
├── requirements.txt            # зависимости проекта
└── README.md                   # описание проекта и инструкция по запуску
```

## Описание данных
Датасет [Default of Credit Card Clients Dataset](https://www.kaggle.com/datasets/uciml/default-of-credit-card-clients-dataset) содержит информацию о клиентах кредитной карты на Тайване с таргетом default.payment.next.month (дефолт в следующем месяце). Включает демографические данные, историю платежей, суммы счетов.

 ### Сервисная архитектура и оркестрация
 
 **Архитектура сервиса** 
 
В данном проекте используется **монолитный подход**. То есть все этапы от обучения до хостинга модели с помощью API разворачиваются как единый сервис. Поскольку проект небольшой по размеру, то для облегчения запуска, тестирования и контейнеризации выбрана именно монолитная архитектура, нет никакой необходимости дробить отдельные этапы на микросервисы. В реальном мире для обеспечения отказоустойчивости и для дальнейшего масштабирования, обеспечения отказоустойчивости микросервисный подход мог бы оказаться более подходящим вариантом (особенно для большого банка)
 
**Концепт брокеров сообщений** 

Брокер сообщений в данном проекте не используется. API обрабатывает запросы клиента в синхронном режиме от получения запроса до вывода результатов инференса. Но в продакшене можно было бы добавить брокер сообщений, например RabbitMQ или Kafka для:
- Асинхронной обработки batch-предсказанийотправки логов запросов и ответов в отдельный сервис
- Обработки событий, связанных с мониторингом качества модели
- Отделения API от тяжёлых фоновых задач
  
В результате у API появилась бы возможность отправлять задачи в очередь и перераспределять нагрузку по воркерам

**Логирование и мониторинг**

В текущей реализации логирование происходит посредством входящих-исходящих запросов модели в JSON формате:
- На вход принимаются пользовательские данные (из инпута в терминале или из JSON-запроса) для инференса
- Модель отдаем в формате JSON: метку предсказния дефолта (0 или 1), вероятность дефолта которую предсказала модель
- В логах сохраяется пользовательского запроса
![](path/to/image.png)

В production-среде такие логи могут собираться централизованно с помощью ELK-стека, Grafana Loki или аналогичных инструментов. Это позволяет отслеживать стабильность API, количество ошибок, распределение предсказаний и возможный drift данных

**Оркестрация (Docker Compose)**

Не реализована

**Обзор инструментов MLops**
- DVC используется для версионирования данных, моделей и артефактов обучения. Он помогает понимать, на какой версии данных была обучена конкретная версия модели.
- MLflow используется для трекинга экспериментов. С его помощью можно сохранять параметры обучения, метрики, версии моделей и сравнивать разные эксперименты между собой.

В данном проекте DVC мог бы использоваться для контроля версий датасета и сохранённых моделей, а MLflow — для сравнения LogisticRegression,GradientBoostingClassifier по метрикам качества
